# Customer 360 requirements

Read-only view of the authorized Customer's current recorded state and independently authorized histories. Logical sections, not an approved screen design or new service topology.

| Section | Content / boundary |
|---|---|
| Overview | Authorized name, type, lifecycle and verification status; no restricted aggregates |
| Basic Information | Accepted applicable Person/Company fields |
| Identity Information | Masked official identifiers unless independent identity-field authority |
| Contact Information | Authorized contact channels and primary indicators |
| Addresses | Authorized address facts according to existing policy |
| Branches | Company Branch records only, resource authorization required |
| Relationships | Authorized related Person, target and business role only; no implied identity/other-resource access |
| Documents | Independent view/download authority; content gated by secure attachment contracts |
| Verification | Status ordinarily readable; evidence restricted; no verification action |
| History | Independently authorized immutable business history; no Audit Reviewer grant implied |

For non-applicable sections (e.g. Branches for an Individual) distinguish not applicable from absent data without leaking restricted presence. Unauthorized sections must not reveal counts, metadata or existence. Exact section disclosure, masking pattern and UI empty/denied behavior remain OPEN. Cross-service Opportunities/Contracts/Orders/Tickets/Projects are future service-owned integrations, not part of current delivery. Customer profile cannot become unrestricted cross-service aggregation.
